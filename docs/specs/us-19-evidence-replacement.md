# US-19: Explain unreadable documents and allow a replacement

Empty files/PDFs, PDFs with no selectable text, partly unreadable PDFs, damaged PDFs and password-protected PDFs now have distinct plain-language explanations in English and German. A PDF with no selectable text may be a scan or image; the UI explicitly says scans are not read automatically. Password-protected and structurally damaged uploads fail before a message/file is saved. Blank and scanned PDFs that can be opened fail reading before any model call. A document with unreadable pages produces no partial suggestions.

Customers can choose Enter details yourself to open and focus the existing fact editor, or type the details in chat. Rejected uploads restore the message draft. No document failure invents facts, rewrites confirmed facts or deletes the rest of the claim.

Replace PDF copy accepts another validated PDF while the claim is editable. The customer sees both filenames before saving. Migration 0013 stores replacement chains, current status, revision and content hash. Earlier files and decisions remain visible; pending suggestions from an earlier copy become superseded and cannot be accepted. Earlier accepted facts remain explicitly confirmed claim facts until the customer changes them. The replacement starts as Uploaded, not yet read, and needs an explicit Read claim PDF action. This story replaces PDF evidence copies; photo analysis/OCR are not added.

Replacement uses the same file, size and bounded validation rules as claim uploads. For uploads with a recorded content hash, identical bytes are rejected with an explanation, while a repeated request after a successful replacement returns the saved version without another file/history event. Conversation/suggestion scope is enforced, and a deferred composite foreign key prevents replacement links across claims while allowing whole-claim deletion. No storage path or public file route is added.

Replacement locks against live reading of the same file and blocks unfinished messages/confirmations. Claim and conversation locks use the same order as claim confirmation/submission. Existing messages, card, policy choice and confirmed facts remain unchanged; history adds the old/new filenames. Failed validation or writes preserve the original copy and state. If a commit acknowledgement is lost, cleanup first checks whether the new file is referenced; an uncertain private file is retained rather than deleting a possibly committed replacement. Reading also preserves suggestions when a fresh read shows the final commit already succeeded.

Customer and reviewer views label current/previous versions clearly. Previous versions have no reading, replacement or confirmation controls. An in-page network retry keeps the original replacement file and target ID; a page reload shows whatever version was saved. Open manual fact drafts and earlier failed actions are preserved before starting another replacement.

Verification uses a synthetic image-only PDF with visible incident/cost text but no selectable text: no OCR/model suggestions are produced. It also covers blank/protected/damaged/empty inputs, replacement replay, source/fact preservation, old suggestion rejection, active reading, failed writes, lost commit acknowledgement, database scope and scoped deletion. The browser flow reads the image-only PDF, opens manual entry, replaces it, loses the response, retries once, reloads versions and continues the full claim/reviewer/history flow. The synthetic scan fixture was rendered and visually checked.

Final local validation: 209 backend tests, 80 frontend tests, Ruff lint/format, TypeScript checking, production build and the full recorded browser flow passed. Self-review resolved commit-acknowledgement safety for files and suggestions, and replacement retries retain their original file/target. No unresolved review findings remain.
