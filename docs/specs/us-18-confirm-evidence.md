# US-18: Confirm document suggestions and resolve conflicts

Each suggestion shows the saved claim value beside the proposed value, its filename, page and quote. Customers can accept or reject pending suggestions individually while the claim is editable. Known values that differ from the suggestion require a separate replacement checkbox. The server checks the submitted baseline against the current saved fact, so an outdated screen cannot silently overwrite a more recent edit. Unknown/null values can be filled without a replacement checkbox. Source decisions are hidden while a manual fact-edit form is open, preserving that draft.

Accepting uses the existing customer-correction path, including field validation, missing-information checks, coverage/risk refresh and before/after history. Complete claims are reassessed; incomplete ones still need their missing facts. A failed reassessment keeps the accepted change, marks guidance out of date and blocks submission until refreshed. Rejecting changes no facts and performs no assessment. Both decisions record a separate source-linked history entry. Reviewers can read decisions and current values; this customer confirmation endpoint never records an adjuster review.

Decisions are final for that suggestion ID. Replaying the same decision returns the current saved claim; it does not reapply a suggestion over later corrections. Trying to reverse the recorded decision is rejected. A customer can still correct the actual claim facts through the normal editor.

Migration 0012 adds the baseline value for a durable applying state. Acceptance reserves that exact suggestion before graph changes, then saves the accepted status, claim/history and messages together. A stable action ID lets an interrupted graph or failed final write finish without duplicating changes or history. While applying, other claim changes, new messages, policy changes and new PDF reading are blocked. Read-only/idempotent replays remain available. Reload shows a Finish document decision action using the saved baseline. A failed rejection can also retry on the current page without changing claim facts.

A stale baseline response reloads current details and requires another explicit decision rather than automatically retrying an overwrite. An earlier failed correction/submission/PDF-reading action keeps its original retry when a new confirmation is attempted. A graph update not yet reflected in the claim row must finish before a new document confirmation can start.

The route requires existing customer access and scopes suggestion lookup through the attachment's conversation. It inherits the shared-demo access model, not private account ownership. Suggestions remain untrusted model output until the customer's explicit choice; accepting a value does not establish that the document or its contents are authentic.

Verification: 198 backend tests and the recorded browser flow cover source decisions, duplicate and concurrent requests, stale baselines, explicit conflict replacement, later manual edits, graph interruption, failed final writes, blocked intervening changes, automatic reassessment and assessment failure. The browser flow compares EUR 900 with a EUR 1200 suggestion, rejects the date suggestion, confirms the amount, recovers a lost response and verifies source/history display through final review.
