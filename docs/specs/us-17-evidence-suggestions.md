# US-17: Read useful facts from claim PDFs

Customers can choose **Read claim PDF** on a verified PDF attachment while a claim is editable. A bounded worker reads selectable text and keeps physical PDF page numbers. A separate structured extraction call proposes supported ClaimFacts fields. It never sends the document body into the conversational claim graph or calls claim-edit/review actions.

Suggestions are stored separately from confirmed facts in migration 0011. Each has a stable ID, field/value, source attachment ID, filename, page, exact supporting quote and pending status. Customer and reviewer screens show them separately with an explicit notice that the claim facts have not changed. They survive reload. Reading the document leaves messages, history, coverage, risk and confirmed claim facts unchanged. Confirmation and conflict handling follow in #75.

Only the known incident/fact fields are allowed; Photos attached, policy, coverage, risk and review state are excluded. Values receive field-specific type/date/time/amount checks. Source quotes must occur on the claimed page; an invalid reference fails the whole extraction rather than publishing unsupported suggestions. Duplicate field/value/page suggestions are removed while conflicting values can remain separate. This verifies provenance, not semantic truth: a model may misinterpret a valid quote, so suggestions still require human checking.

The system prompt treats filenames and PDF text as untrusted data, forbids following embedded instructions and requests only the constrained fact schema. No tools capable of changing claims or accessing external resources are exposed to this extraction step. Text and quotations are displayed as plain text. These controls keep document instructions from authorizing claim changes; they do not claim perfect model interpretation or prompt-injection detection.

PDF parsing is limited to 300 pages and 40,000 text characters, with a 30-second worker timeout, CPU limit and memory limit where supported. Oversized text is rejected rather than silently truncated. Empty/unreadable pages with content fail visibly; blank spacer pages are preserved. There is no OCR, image analysis, currency conversion or automatic analysis at upload. Parsing runs in a bounded worker, not an operating-system sandbox. Only this attachment's text is sent to the existing configured model provider.

The authenticated extraction route requires both conversation and attachment IDs to match. It follows the shared demo credential rules, not private customer account ownership. It adds no public file route and returns no storage paths. PostgreSQL advisory locking prevents duplicate work; ready results are replayed without rereading or calling the model. Failed/stopped processing can be explicitly retried. Suggestions and ready state commit atomically; a failed write is not displayed as ready. Network failure retries the same attachment rather than sending another chat message.

Verification covers real two-page repair-estimate/police-report text; strict field validation; page/quote grounding; untrusted instruction separation; access and claim scope; concurrent extraction; provider failure; database failure; stable replay; and unchanged confirmed facts. The synthetic claim_evidence.pdf fixture is clearly marked as sample data and was visually checked on both pages.

Local validation: 190 backend tests, 73 frontend tests, Ruff lint/format, TypeScript checking, production build and the full recorded browser flow passed. The browser flow reads a real PDF, recovers a lost extraction response, reloads saved suggestions, verifies confirmed amounts remain unchanged and shows the same sources to the reviewer.
