# US-20: Keep the document checklist in sync with saved evidence

The previous unsaved checkboxes are replaced by a saved checklist. Each request has a stable ID, label, source and one of three states: Missing, Uploaded (awaiting reviewer check), or Confirmed by reviewer. Uploading a file or accepting an extracted fact cannot confirm document completeness. The checklist is separate from the human claim-review decision and does not add a new approval/submission gate.

Migration 0014 stores checklist requests and decisions on the claim. Existing current-card document requests are backfilled without inventing confirmations. New assessment requests are saved when a card is written and retained when a later model answer stops mentioning them. Requests from before this feature that are absent from the latest stored card cannot be reconstructed. Read endpoints do not create or mutate requests.

Assessment labels that unambiguously mention photos, repair estimates or police reports can match current verified uploads of that declared purpose. This is an upload association, not validation of the contents. Ambiguous/custom labels require an explicit file link. Customers can link or unlink current files before submission; exclusions survive reload and replacements. A generic Other document can be explicitly linked to a report/estimate request. PDFs and non-photo-purpose images cannot fill a damage-photo request. Unverified legacy files and separate policy PDFs do not count. The Photos attached fact alone never completes a document item.

Reviewers can select requested document types or enter a custom document label when asking for more information. Those requests have their own saved identities and request times. Older files are not automatically reused for a new reviewer request; a new matching upload or explicit customer link is needed. A plain question with no selected document request does not invent a file requirement. A repeated recovery of the same review action does not create duplicate requests.

Only the adjuster credential can confirm the exact currently linked file IDs while a claim awaits review. Confirmation means the reviewer chose to mark those documents checked; it is not an automated authenticity or sufficiency claim. A stale set of file IDs is rejected. Confirmation can be cleared. History records file links/unlinks and confirmation/clearing, including filenames and versions. The reviewer credential stays in memory.

Current file versions determine upload state. Replacing a linked document follows the new version for the same request, but the earlier version's confirmation does not transfer: the new copy is Uploaded until checked again. Manually excluded/link-selected families follow their replacement chain. Cross-claim and mismatched file links are rejected. Failed/in-progress reading can still be Uploaded, with its reading failure displayed, while never being automatically Confirmed.

Customers and reviewers receive the same checklist in conversation/claim responses. Link retries are idempotent, retain the original action and do not send another chat turn. An outdated reviewer confirmation reloads the latest copies and requires another explicit choice. Pending-message/confirmation guards and the existing claim/conversation lock order protect mutations. New files continue to use the existing collecting/information-needed conversation upload flow; existing files can be linked while assessed.

Verification covers saved/reloaded states, reviewer-only confirmation, duplicate requests, replacement invalidation, fresh reviewer requests, manual links and exclusions, generic-file relevance, cross-claim/type rejection, policy-file exclusion, and a photo fact without a real photo. UI tests verify that linking does not change the displayed server state locally or expose customer confirmation controls. The recorded browser flow shows Missing/Uploaded/Confirmed, requests new evidence, links an older file explicitly, reloads and confirms it in the next review.

Final local validation: 214 backend tests, 84 frontend tests, Ruff lint/format, TypeScript checking, production build and the recorded browser flow passed. Self-review resolved linking generic verified files to typed requests and preserved confirmation source filenames/versions in history. No unresolved review findings remain.
